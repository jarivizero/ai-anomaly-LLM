## Core Concepts
Understanding these primary building blocks will help you get the most out of OpenPipe.
## Data Collection & Logging
OpenPipe acts as a proxy or wrapper around your LLM provider calls, enabling automatic, zero-latency data ingestion.
## The SDK Wrapper
The OpenPipe SDK wraps your standard OpenAI or Mistral clients. When you make a call, the request and response are processed asynchronously:

* Zero-latency overhead: The log data is sent to OpenPipe's servers in a background thread or asynchronous task, meaning it never blocks your application's primary API response.
* Fallbacks: If the OpenPipe logging endpoint goes down, the SDK catches the error internally, ensuring your production application remains unaffected.

## Data Privacy & Security
Data privacy is a foundational design choice at OpenPipe:

* No Third-Party Training: OpenPipe never uses your data, prompts, or completions to train its own baseline models or any models belonging to other customers.
* Data Isolation: All data uploaded or logged to your account is strictly isolated within your organization's workspace.
* Encryption: Data is encrypted in transit via TLS 1.3 and at rest using industry-standard AES-256 encryption.
* Retention Control: You can permanently delete logs or entire datasets from the dashboard at any time, removing them completely from OpenPipe infrastructure.

## Sampling Strategies
When dealing with high-volume production traffic, logging 100% of requests can create massive, redundant datasets and increase costs unnecessarily. OpenPipe provides sampling configurations to filter and throttle data ingestion:

* Random Sampling: Log a fixed percentage of all requests (e.g., log only 10% of traffic).
* Conditional/Tag-Based Filtering: Only log requests that match specific metadata tags or are routed to particular features in your app.
* Exclusion Rules: Prevent specific sensitive operations or data fields from being sent to OpenPipe entirely by disabling the openpipe configuration parameter on those specific API calls.

## Datasets & Data Management
Datasets are curated collections of prompts and responses used to train and evaluate your fine-tuned models.

       [ Production Logs ] --------+
                                   |---> [ Filter / Curate ] ---> [ Dataset ]
       [ Uploaded JSONL Files ] ---+

## Creating Datasets
You can build a dataset in two ways:

   1. From Logs: Select a set of captured production logs in the dashboard and add them to a new or existing dataset.
   2. Via File Upload: Directly upload a .jsonl file containing prompt-response pairs formatted in the standard OpenAI Chat Completion structure.

## Dataset Splits (Train vs. Test)
When you create a dataset, OpenPipe automatically splits your data into two distinct groups to ensure rigorous evaluation:

* Training Set (typically 80-90%): The actual examples the model learns from during the fine-tuning process.
* Test/Validation Set (typically 10-20%): A held-out set of examples that the model never sees during training. This set is used after training to calculate objective performance metrics (like accuracy or token match) against a known baseline.

## Data Curation Best Practices
The quality of your fine-tuned model depends entirely on the quality of your dataset. Follow these guidelines to optimize your data:

* Deduplication: Remove highly repetitive or near-identical prompts. A diverse dataset helps the model generalize better to novel inputs.
* Prune Low-Quality Outputs: Filter out instances where the baseline model gave a poor, truncated, or incorrect answer. Replace them with ideal corrections.
* Balance Class Distributions: If you are training a classification model, ensure all target classes (e.g., "Refund", "Technical Support", "Feedback") are well-represented, rather than heavily skewed toward a single category.
* Handle Edge Cases: Intentionally include rare or complex examples that the baseline model typically struggles with.

## Fine-Tuning & Evaluation
Fine-tuning adapts a smaller, more efficient open-source model to mimic or exceed the performance of large LLMs for your specific workload.
## Training Process & Pipelines
OpenPipe implements a multi-step training pipeline that optimizes the model far beyond vanilla fine-tuning:

   1. Format Standardization: Inputs are structured cleanly using appropriate prompt templates corresponding to the selected base model (e.g., Llama or Mistral templates).
   2. Hyperparameter Optimization: OpenPipe automatically tunes learning rates, batch sizes, and epoch counts based on your dataset size to prevent overfitting.
   3. Full-Parameter vs. LoRA: Depending on the model size and workload requirements, OpenPipe utilizes highly optimized training regimes to maximize model expression and adaptability.

## Evaluation Metrics
After a fine-tuning run completes, OpenPipe runs the model against your held-out Test Set and displays comprehensive metrics in the dashboard:

* Test Loss: Measures how closely the model's token probabilities align with the expected target answers. Lower loss indicates better alignment.
* Win Rate (vs. Baseline): OpenPipe can run an automated judge (such as GPT-4) to evaluate and compare the fine-tuned model's responses against the original base model or the original training target, giving you a clear win/loss/tie ratio.
* Token Overlap/Accuracy: For deterministic or structured outputs (like JSON or single-word classifications), this tracks the percentage of exact matches against your validation targets.

* Dedicated Cold-Start Optimization: Models are optimized for fast loading onto GPU clusters.

* Edge Routing: Requests are routed efficiently to the nearest active cluster to minimize network round-trip time.

## Advanced Guides## RAG & Context Distillation
When building Retrieval-Augmented Generation (RAG) systems, developers often pass massive amounts of context (search results, documentation, database rows) into the prompt to ensure accuracy. This introduces significant problems:

* High Latency: Processing thousands of context tokens increases Time-to-First-Token (TTFT).
* High Cost: You pay for a massive number of input tokens on every single query.
* Context Stuffing / Lost in the Middle: Large models often ignore information buried in the middle of long prompts.

## Distillation Workflow
OpenPipe allows you to use Context Distillation to train a smaller model to reason as if the context were there, or to extract and summarize key elements using a fraction of the original token footprint.

[User Query + 10kb Context] ---> ( GPT-4o / Source Model ) ---> [High Quality Answer]
                                                                        |
                                                    ( Logged & Trained via OpenPipe )
                                                                        v
[User Query + 1kb Context] ------> ( Fine-tuned Llama 3.1 8B ) -> [High Quality Answer]


   1. Collect Teacher Logs: Run your production RAG pipeline using a large model (e.g., GPT-4o) with full, verbose context. Log these transactions through OpenPipe.
   2. Filter and Curate: Create a dataset from these logs.
   3. Compress the Inputs (Optional): Modify the dataset training inputs to only include a highly condensed version of the context, or just the raw user query and the teacher's high-quality answer.
   4. Train the Student: Fine-tune a smaller model (like Llama 3.1 8B). The student model learns to infer the background knowledge and structural formatting directly from the teacher's outputs, eliminating the need to pass massive reference texts on every future inference call.

## Structured Outputs & JSON Enforcement
Getting standard LLMs to reliably output valid JSON that matches a strict schema can be incredibly frustrating. Prompt engineering often fails under edge cases, leading to broken application logic.
Fine-tuning with OpenPipe provides a native, highly reliable way to enforce structured outputs.
## How to Fine-Tune for JSON

   1. Format your Training Data: Ensure your target completions in your dataset are valid stringified JSON objects.
   2. Provide consistent schemas: Keep the input system prompt or instruction structure identical across your dataset.

## Code Example: Requesting Structured Data
When querying your fine-tuned model, you can combine the model's learned structure with OpenAI-compatible response_format parameters to guarantee 100% syntactical validity.
=== "Python"
```python
import json
from openpipe import OpenAI
client = OpenAI()
# Define the schema you want to enforce
json_schema = {
"name": "CustomerExtraction",
"schema": {
"type": "object",
"properties": {
"name": {"type": "string"},
"order_id": {"type": "integer"},
"status": {"type": "string", "enum": ["shipped", "pending", "cancelled"]}
},
"required": ["name", "order_id", "status"],
"additionalProperties": False
},
"strict": True
}
completion = client.chat.completions.create(
model="openpipe:your-json-model-id",
messages=[
{"role": "system", "content": "Extract customer order metadata."},
{"role": "user", "content": "Hey, it's John Doe. Can you check on order 94821? I hope it shipped."}
],
response_format={"type": "json_schema", "json_schema": json_schema}
)
# The output is guaranteed to follow the schema and match your fine-tuned style
data = json.loads(completion.choices[0].message.content)
print(data["name"]) # "John Doe"
print(data["order_id"]) # 94821
```

## Effective Model Evaluation & Iteration
Fine-tuning is an iterative engineering process. To continuously improve your model, establish a robust evaluation loop.

graph LR
    A[Train Model] --> B[Evaluate Test Loss]
    B --> C[Analyze Edge Cases]
    C --> D[Augment Dataset]
    D --> A

## Step 1: Analyze Test Loss and Win Rates
Look at your model's dashboard after training. If the Test Loss starts increasing while Train Loss decreases, your model is overfitting. Reduce the number of epochs or increase the diversity of your training data.
## Step 2: Hard Negative Mining
Identify the specific examples in the evaluation set where the model failed or received a low score from the automated judge.

* Are there commonalities among the failures? (e.g., they all involve negative numbers, or foreign languages).
* Isolate these "hard cases".

## Step 3: Dataset Augmentation
Add more variations of these specific hard cases into your training dataset. If the model struggles with short, one-word queries, inject 50 high-quality examples of short queries with correct responses into your next training version.
## Step 4: Version Control Your Models
Treat your datasets and models as code versions. OpenPipe allows you to fork datasets and maintain clear lineage trails so you can easily roll back to a previous model iteration if performance drops on general capabilities.

## Troubleshooting & FAQ## Frequently Asked Questions## How much data do I need to see a noticeable improvement?
For simple style alignment, formatting enforcement, or classification tasks, you can see significant improvements with as few as 50 to 100 high-quality examples. For complex reasoning, domain-specific translation, or heavy context distillation, we recommend 1,000 to 5,000+ examples.
## Does OpenPipe support fine-tuning on completion models (base models without chat templates)?
OpenPipe is heavily optimized for the Chat Completions API format. If you have raw text data, we recommend structuring it into a user and assistant message format inside a standard JSONL structure before importing it.
## What happens if OpenPipe's servers go down mid-request?
The OpenPipe SDK uses a non-blocking asynchronous architecture for logging. Your application's request goes straight to the primary LLM provider (like OpenAI). The logging payload is handled on a separate thread worker. If OpenPipe is unreachable, the log is dropped gracefully, and your user experiences zero downtime or latency penalty.
## Can I export my model weights?
Yes. OpenPipe values open ecosystems. If you wish to migrate your fine-tuned model weights to your own self-hosted infrastructure (e.g., using vLLM or Hugging Face TGI), you can request a weights export directly through our enterprise support channel.
